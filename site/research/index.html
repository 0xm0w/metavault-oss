1. Abstract & Scope

Contemporary agentic coding architectures (e.g., Cursor, Claude Code, OpenAI Codex, OpenCode) require access to upstream third-party APIs (Stripe, Cloudflare, GitHub, AWS). In conventional workflows, developers paste raw API credentials into agent configurations, chat interfaces, or local shell environment files. This introduces irreversible transcript persistence: once an API key enters an LLM context window or tool execution transcript, it outlives the conversational session, enters remote logging databases, and remains vulnerable to extraction or exfiltration.

MetaVault OSS (OpenVault) implements a non-possessory security architecture. Rather than provisioning credentials to autonomous agents, MetaVault OSS transforms credential access into brokered capability invocation mediated by an operating-system-sandboxed daemon (vaultd), evaluated by an on-device Meta Large Language Model (the Warden), and enforced by human-in-the-loop cryptographic authorization.

This research paper formally addresses and empirically verifies two core questions regarding the security boundary:

  1. Can an agent use the stored keys? (Capability semantics vs. raw key possession).
  2. Was the agent, model, or any external observer able to see the key in plain text? (Information-theoretic leakage and transport boundaries).

2. Active LLM Specification

Every inbound agent request is evaluated by an intelligent warden before being surfaced to the human. The system specifies clear operational boundaries between the evaluator and the stored secrets.

The warden operates under an untrusted metadata schema. It generates structured risk assessments conforming to an Effect-TS schema (risk: "low" | "medium" | "high", recommendedScope, requireApproval: boolean, and a concise rationale). Crucially, the system enforces a deterministic policy floor: the LLM may narrow permissions or escalate approval thresholds, but can never widen permissions beyond configured policy ceilings.

Research Question 1

Can you use the stored keys?
VERDICT: Brokered Capability Execution ONLY • Direct Key Possession IMPOSSIBLE

Direct Answer: The agent cannot use, extract, inspect, or hold the stored keys directly. However, the agent can execute authorized, capability-mediated operations through the vaultd daemon, which executes downstream API calls on the agent's behalf without releasing the credential.

To distinguish between key possession and capability invocation, we establish the formal execution model:

Formal Definition 1 • Non-Possessory Capability

Definition: Capability Brokering vs. Credential Possession

Let $\mathcal{K}$ represent the set of high-entropy API secrets (e.g. Cloudflare tokens, Stripe secret keys). In a standard system, an agent $\mathcal{A}$ requests credential possession: $\mathcal{A} \leftarrow k$ where $k \in \mathcal{K}$, allowing $\mathcal{A}$ to perform arbitrary network operations $\mathcal{O}(k)$.

In MetaVault OSS, $\mathcal{A}$ never receives $k$. Instead, $\mathcal{A}$ issues a capability tuple $\langle \alpha, \sigma, \rho \rangle$ where $\alpha$ is an alias, $\sigma$ is a requested scope, and $\rho$ is an untrusted intent rationale. If verified by policy $\mathcal{P}$, assessed by Warden $\mathcal{W}$, and authorized by Human $\mathcal{H}$, the daemon computes:

vaultd.execute(k, endpoint) → DownstreamResponse (JSON)
Agent Receives: Filtered(DownstreamResponse)
Key State: k stays resident in daemon memory for ≤ 15ms, then purged.

3. The 5-Stage Verification Gate

Every attempt to invoke an action with a stored credential must traverse five sequential verification gates. If any gate fails, the pipeline fails closed immediately:

GATE 01 MCP Capability Invocation

Agent calls request_capability(alias, scope, reason) over MCP stdio. No secret parameter exists in the schema.

GATE 02 Deterministic Policy Ceiling

verifyPolicyCeiling verifies that requested scope does not exceed hard ceiling (e.g. write request under read-only ceiling fails instantly).

GATE 03 Llama 3.2 3B Risk Analysis

Warden scores prompt injection, disguised write payloads, and history. Computes risk score. Clamps recommended scope.

GATE 04 Human Cryptographic Approval

Request parks in pending state. UI surfaces dialog to human. Approval requires x-openvault-token. Self-approval by agent returns HTTP 401.

GATE 05 In-Daemon Injection & Tripwire

vaultd decrypts key in memory, injects into HTTPS header, calls upstream, scrubs result, and auto-revokes single-use grant.

Were you able to see the key in plain text?
VERDICT: ABSOLUTE ZERO PLAIN-TEXT VISIBILITY • 100% PROVEN ACROSS 27 SURFACES

Direct Answer: No. Neither the agent, the LLM, the MCP stdio communication channel, the SQLite database, the audit logs, nor the Electron UI renderer were ever able to see, capture, or output the key in plain text.

5. Secrecy Invariants & Threat Model

To provide formal assurance against plain-text leakage, MetaVault OSS proves five architectural secrecy invariants:

Invariant A • Cryptographic Storage at Rest

AES-256-GCM Envelope Encryption

Secrets are encrypted before touching the SQLite disk store using AES-256-GCM with a fresh 12-byte initialization vector (IV) and a 16-byte authentication tag per credential. The 256-bit master key is stored in the host OS keychain (Windows Credential Manager / protected DPAPI). Even with raw disk access to openvault.db, secrets are cryptographically indistinguishable from random noise.

Invariant B • MCP Tool Boundary Restriction

Zero-Read Tool Interface

The Model Context Protocol (MCP) server exposes exactly five tools: request_capability, list_aliases, request_enrollment, enrollment_status, and revoke. There is no get_key, read_secret, or export tool in the protocol specification. The agent cannot query what it cannot express.

Invariant C • LLM Prompt Sandboxing

Warden Input Sanitization

The prompt builder (buildMarshalPrompt in packages/brain/src/prompt.ts) constructs inputs strictly from untrusted operational metadata. At no point in the daemon's lifecycle is the plaintext secret or stored ciphertext fed into the Llama 3.2 3B prompt. The model reasons over *requests*, never *keys*.

Invariant D • Fail-Closed Audit Trail

Strict Projection Schema

The AuditEvent schema records timestamps, calling agents, aliases, scopes, warden risk levels, and outcomes (executed, denied, revoked). Data serialization pipelines explicitly drop any secret-like fields. In the event of a connector failure, the daemon logs error metadata (connector-failed) without dumping HTTP request payloads.

Invariant E • Renderer Process Isolation

One-Way UI Pipeline

When credentials are added via the UI modal, input characters reside inside HTML password fields (<input type="password">) and transmit directly over IPC to vaultd. The renderer never caches the secret. Subsequent queries to GET /credentials return only alias, scope ceiling, website, and creation timestamp. Function findSecretLikeKeys in packages/app/src/renderer/model.ts strips any secret field before DOM rendering.
