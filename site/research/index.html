Research · the thesis

The vault holds the line. The warden reads the intent.

The vault is deliberately dumb: hard ceilings, fixed rules, safe with no model at all. The warden is a Meta model that catches requests that sound routine but aren't.

A barista checks the name on the cup. The warden checks what the order is for.
Held-out set: rules alone caught 12/28 · rules + Muse Spark 1.3 caught 27/28

Warden numbers are Muse Spark 1.3 via the Meta API. Local Muse Glimmer through Ollama is supported; we publish no local numbers.

Zero-Context Agentic Vault · the practical winner

For existing APIs, zero-context custody wins.

Call Stripe without handing its key to the agent. The broker supplies the authentication the API accepts. A standalone ZK proof cannot replace that credential. This is the advantage we optimize for.

1 · Request

Ask by alias and scope

The agent supplies a reason, not a stored key. request_capability({alias: 'stripe', scope: 'charges.read', reason: 'List charges'})

2 · Warden

Vet metadata, not the key

Agent, IDE, tool, alias, scope, reason, request/denial counts and policy digest enter the prompt. The stored target credential does not.

3 · Transport

Inject inside the daemon

After authorization, vaultd decrypts the credential and the connector adds a bearer header to a preset HTTPS request.

4 · Return

Return the result

No credential-read MCP tool. Headers and failed response bodies are omitted. Successful bodies pass through; response hardening is tracked separately.

Code review: four boundaries, evidence and limits. "Zero-context" describes credential custody, not an agent with no task context.

Architecture decision · goal, choice, trade-off

Custody executes the call. A proof verifies a claim.

Choose brokered custody for agent-safe access to existing APIs. Keep keys out of the agent's request and prompt while preserving the service's normal authentication.

Decision criterionWhy custody wins hereTrade-off considered
Call an unchanged APIThe daemon injects a credential that Stripe accepts. No proof verifier or new authentication protocol is required at the service.Trust the unlocked daemon, local runtime and HTTP stack with plaintext credentials.
Keep keys out of agent contextThe agent requests an alias and scope, not the stored key. The warden assesses metadata, not that credential.Custody separation is not cryptographic proof of correct execution, nor protection from a compromised host.
Use ZK instead?A standalone proof is not an accepted substitute for Stripe's documented key/token authentication. It does not complete this job alone.ZK can add independently verifiable claims or policy receipts at a different boundary. That is additional machinery, not a replacement broker.
Ship a focused integrationThree preset GET connectors already cover Stripe charges, GitHub repos and Cloudflare token verification.More operations, signing schemes and token refresh need connector work. No universal compatibility or measured latency win is claimed.

Decision reasoning in this review, not a claim about historical intent. zkTLS can authenticate web data while normal server authentication remains. Stripe auth · zkVM receipts · MPC-TLS

Implementation gaps · separate from the design decision

Harden the implementation. Keep the custody advantage.

Model boundary

Metadata can leave the device

Default: Muse Spark 1.3 via the Meta API. Local inference is a bring-your-own endpoint, not a bundled model. The model prompt excludes stored target secrets, but agent-written reasons can contain sensitive text.

Memory boundary

No immediate RAM-scrub guarantee

Decryption produces a JavaScript string. Credential and HTTP-runtime copies have no guaranteed erasure time. Passphrase mode zero-fills its held master-key buffer on lock; that is a different claim.

Response boundary

Not a general-purpose sanitizer

A successful upstream response is parsed and returned, not scanned for echoed keys or other secrets. Hostile or sensitive response content remains a risk.

Execution boundary

Brokered MCP is not CLI export

metavault run decrypts non-card credentials into a child environment. That mode is outside the zero-context claim. Local malware can still keylog or read an unlocked process.

At rest: AES-256-GCM. Default new vaults use a passphrase-wrapped master key, not merely OS-keychain custody. Legacy keychain/env modes have different protection. No formal-verification claim.

Research directions · not shipped features

Add proofs where verification is the job.

Selective disclosure

Prove an issued claim

BBS-style credential proofs can reveal selected signed facts without exposing the full credential. A spend-limit claim needs an issuer, fresh data and a proof design; an API key alone is not that credential.

Policy receipts

Prove a defined computation

Explore zkVM receipts tied to a reviewed policy program and authenticated inputs. Proving a policy check does not by itself prove which HTTP request was sent or what the remote service did.

Encrypted team sync

Keep the server out of key custody

Client-side encrypted sync needs key distribution, recovery, revocation and device security. This is often marketed as "zero knowledge," but it is not the same primitive as a ZK proof. Neither is implemented here.

Web-data provenance

Prove what a server returned

TLSNotary uses MPC-TLS to authenticate exchanged data with selective disclosure. It is not a blanket proof of payment settlement or a replacement for credentials. Protocol and verifier/notary assumptions matter.

These are optional verification directions, not prerequisites for the brokered API design. Hardening priorities: successful-response handling, CLI export review, memory exposure and matched workflow benchmarks. No new model calls or proof benchmarks were run for this review. The dumb vault

Safe with no model at all

The warden can tighten a decision. It can never loosen one. Every arm, even no warden, held all 4/4 policy-floor cases.

1

Writes always ask

Refund, push, delete: you decide, whatever the model says.

2

Ceilings are hard

Above the ceiling is denied. Nobody gets asked.

3

No cross-resource hops

A grant for one resource can't open another.

4

Model down → you decide

Timeout or bad JSON goes to approval. Never waved through.

Guarantees should be deterministic. The model should advise.CaMeL (Debenedetti et al., 2025) · Design Patterns for Securing LLM Agents (Beurer-Kellner et al., 2025)

Why: prompted LLM judges are unreliable alone. In R-Judge (Yuan et al., 2024) most models scored near random at spotting unsafe agent behaviour. The four checks live in packages/core/src/policy.ts and run before any model.

The scary part · what MetaVault does instead

A saved card the agent can't read

Payment cards

Brand and last 4, nothing more

Number (Luhn-checked), name, expiry and CVV are stored as one AES-256-GCM ciphertext. Agents, MCP and the app see brand, last 4 and a mask.

Every card use is a financial high-risk write: always a human, never auto-approved, never lowered by the warden. No payment connector exists yet, so an approved card grant is refused.

Honest scope

Not end-to-end, not autofill

No browser autofill or checkout. The daemon holds the master key while unlocked, so it is not end-to-end encrypted against its own machine.

What it is: encryption at rest, a passphrase-wrapped key with auto-lock, a policy gate, and no card value handed to the agent. pqc.ts (ML-KEM-768 + X25519) is built and tested, not yet used for storage.

Skeptic's corner · the evidence

What this does not prove yet

1

Same author wrote both sides

I wrote the rules and the cases. Freezing rules first reduces the bias; it doesn't remove it.

2

Small n

28 risky, 28 benign. One case moves a rate ~3.6 points. Directional, not a leaderboard.

3

Adaptive attackers

The Attacker Moves Second (Nasr et al., 2025) broke 12 recent defenses. The warden is a second layer, which is why the floor exists.

4

No barista stopwatch

Human approval speed is unmeasured. The claim is narrower: the warden decides before the request reaches you.

Skeptic's corner · the protection

What the vault does not stop yet

5

Keyloggers get the passphrase

scrypt (N=217, r=8, p=1) or Argon2id (19 MiB, t=2, p=1) slows offline guessing. It does nothing against recorded typing.

6

Unlocked means readable

The master key sits in daemon memory while unlocked. Node offers no mlock or MADV_DONTDUMP. Auto-lock shortens the window; it doesn't close it.

7

OS prompts: researched, not built

Windows Hello, macOS LAContext and polkit don't guard the key yet. The app's Hello lock only hides the window.

8

The daemon token is a key too

Whoever reads metavault.token can try unlocks (5 free, then 30 s → 15 min backoff), lock, or add a card. It can also call /approve. It can never read a secret back; an approved card use fails only because no payment connector exists yet.
